# DoQA Test Case Review Rules v1.10.0

## 1. Название тест-кейса

### 1.1. Обязательные смысловые блоки

- **Что делаем** — обязательный блок (операция / действие).
- **Где делаем** — опциональный блок (объект / экран / страница).
- **При каком условии** — опциональный блок (контекст / предусловие).

### 1.2. Запрещённые стоп-слова в начале названия

- «Проверка»
- «Проверять»
- «Тестирование»
- «Тест»

### 1.3. Формат

- Допустим формат с символом `_` (underscore) как разделитель смысловых блоков, если это принято в проекте.
- Дубликат — одинаковая по смыслу операция в одинаковом условии.
- Поиск дубликатов выполняется только если переданы связанные кейсы.

---

## 2. Описание

### 2.1. Обязательность

- Поле `description` **обязательно**.
- Краткая business rule или пользовательский сценарий полезны, но не обязательны.

### 2.2. Ссылки

- Ссылка на требование или задачу **опциональна**.
- Отсутствие ссылки даёт предупреждение, но не снижает оценку.
- **Запрещается** выдумывать ссылку, задачу, требование или тип теста.

### 2.3. Тип теста

- Тип теста **обязателен**.

---

## 3. Предусловия

- Предусловие описывает **готовое состояние** системы.
- Допустима явная команда технической подготовки браузера.
- Команда подготовки не снижает оценку и не делает кейс ручным автоматически.

---

## 4. Тестовые данные

### 4.1. Конкретность

- Каждое значение должно быть **конкретным**.
- Допустимы литералы.
- Допустимы понятные правила генерации.
- Допустимы однозначные именованные ссылки на ранее сохранённые значения.
- Допустимы параметры DoQA, если они размечены как параметры DoQA.
- Обычный текст с тем же названием **не считается** параметром.

### 4.2. Разрешённые вычисляемые значения

- сегодняшняя дата
- текущая дата и время
- вчера
- послезавтра
- на N дней раньше / позже
- на N часов раньше / позже
- на N минут раньше / позже

### 4.3. Не поддерживаются

- Месяцы
- Годы
- Рабочие дни
- Праздники
- Именованные часовые пояса
- Произвольные формулы

### 4.4. Запрещённые заглушки

- «как обычно»
- «любое подходящее значение»
- «любое значение»
- «произвольное значение»
- «на усмотрение»
- «что-нибудь подходящее»
- «todo»
- «тбд»
- «уточнить»

---

## 5. Конфигурации прогона

- Реальные учётные данные **запрещены**.
- Адрес тестового стенда **не должен** быть жёстко прописан в шагах.
- Адрес стенда передаётся через конфигурацию прогона.
- Формулировки «базовый URL» и «base URL» допустимы.
- Абсолютные адреса сторонних сервисов, тестовые данные, ссылки и redirect-адреса **не считаются** адресом стенда.

---

## 6. Шаги

### 6.1. Общие требования

- Каждый шаг — **конкретное действие**.
- Используется **одна грамматическая форма**: инфинитив или повелительное наклонение.
- В ячейке действия должны быть **действия**, а не проверки.

### 6.2. Элементы интерфейса

- Описываются **видимыми признаками**: роль, текст, подпись, placeholder, tooltip, видимый контекст.
- **Не требуются** DOM-селекторы и технические идентификаторы.
- Названный тип элемента сохраняется: кнопка остаётся кнопкой, поле — полем, столбец — столбцом.

### 6.3. Ветвления

- **Ветвления запрещены.**
- Каждая ветка должна быть отдельным тест-кейсом.
- Максимальная длина инструкции: **2000 символов**.

### 6.4. Маркеры ветвления

- «если появится»
- «если отображается»
- «если будет»
- «при наличии»

Список не исчерпывающий, нужна семантическая проверка.

---

## 7. Ожидаемые результаты

### 7.1. Структура

Ожидаемый результат отвечает на два вопроса:
1. Что произошло?
2. Какой наблюдаемый признак это подтверждает?

### 7.2. Объективные признаки

- Текст
- Значение
- Состояние
- Число объектов
- URL
- Изменение данных
- Формат
- Непустота
- Диапазон
- Принадлежность набору
- Сравнение с прежним значением

### 7.3. Требования

- В ожидаемом результате должны быть **проверки**, а не команды.
- **Запрещены** субъективные формулировки.
- Результат описывает **состояние системы**, а не действие пользователя.
- Для свободного текста по умолчанию проверяется **вхождение**.
- Полное совпадение используется только если это требуется по смыслу.
- Если нужно несколько фрагментов текста, порядок не важен, если явно не указано иное.
- Тип и контекст элемента являются частью требования.
- Сообщение в конкретном поле проверяется **в этом поле**.
- Ошибка валидации поля проверяется как сообщение этого поля.
- Максимальная длина ожидаемого результата: **2000 символов**.

### 7.4. Запрещённые формулировки

- «всё корректно»
- «правильный результат»
- «операция выполнена успешно»
- «данные отображаются корректно»

---

## 8. Автоматизация

- Ограничения автоматизации **не снижают** качество текста тест-кейса.
- Если автоматизируются все действия и проверки — статус: **«Подлежит автоматизации»**.
- Если хотя бы одно действие или проверка не поддерживается — статус: **«Ручной»**.
- Неопределённый результат остаётся дефектом текста независимо от статуса автоматизации.
