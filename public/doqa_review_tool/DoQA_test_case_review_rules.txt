============================================================
ПРАВИЛА ПРОВЕРКИ ТЕСТ-КЕЙСОВ (DoQA_test_case_review_rules)
============================================================

1. СТРУКТУРА ТЕСТ-КЕЙСА
-----------------------
1.1. Название тест-кейса должно быть информативным и отражать суть проверки.
     - Допустимо: "Авторизация пользователя с валидными данными"
     - Недопустимо: "Тест 1", "Проверка", "Тестирование входа"
     
1.2. Название должно начинаться с существительного или глагола в инфинитиве.
     - Допустимо: "Проверка отображения...", "Валидация поля..."
     - Недопустимо: "Что будет если...", "Нажать кнопку..."

1.3. Описание тест-кейса должно содержать цель проверки.
     - Если описание пустое — это нарушение.

1.4. Предусловия должны описывать состояние системы ДО начала теста.
     - Должны быть конкретными и выполнимыми.
     - Недопустимо: "Система готова" (слишком абстрактно)
     - Допустимо: "Пользователь зарегистрирован и авторизован в системе"

1.5. Постусловия должны описывать действия после завершения теста (если необходимы).
     - Например: очистка тестовых данных, выход из системы.

2. ШАГИ ТЕСТ-КЕЙСА
-------------------
2.1. Каждый шаг должен содержать ДЕЙСТВИЕ (что сделать).
     - Действие должно быть конкретным и однозначным.
     - Недопустимо: "Проверить что-нибудь", "Посмотреть"
     - Допустимо: "Ввести в поле 'Email' значение 'test@example.com'"

2.2. Каждый шаг должен содержать ОЖИДАЕМЫЙ РЕЗУЛЬТАТ.
     - Ожидаемый результат обязателен для каждого шага.
     - Должен быть проверяемым и конкретным.
     - Недопустимо: "Всё работает", "Ошибок нет", "Должно сработать"
     - Допустимо: "Отображается сообщение 'Вход выполнен успешно'"

2.3. Действие и ожидаемый результат не должны дублировать друг друга.
     - Недопустимо: Шаг "Нажать кнопку Сохранить" → ОР "Кнопка Сохранить нажата"
     - Допустимо: Шаг "Нажать кнопку Сохранить" → ОР "Форма сохранена, отображается уведомление"

2.4. Шаги должны идти в логической последовательности.
     - Нельзя пропускать необходимые промежуточные действия.
     - Нумерация должна быть сквозной.

2.5. Каждый шаг должен быть атомарным — содержать одно действие.
     - Недопустимо: "Ввести email, нажать кнопку Войти и проверить результат"
     - Допустимо: разделить на 3 отдельных шага

3. ТЕСТОВЫЕ ДАННЫЕ
-------------------
3.1. Если шаг требует ввода данных, тестовые данные должны быть указаны.
     - Недопустимо: "Ввести данные" (без указания каких именно)
     - Допустимо: "Ввести в поле 'Логин' значение 'user_test'"

3.2. Тестовые данные должны быть реалистичными и валидными (для позитивных тестов).

3.3. Для негативных тестов данные должны быть заведомо невалидными с указанием причины.

4. ПРИОРИТЕТ И СТАТУС
-----------------------
4.1. Приоритет должен соответствовать важности функциональности:
     - Высокий: критичный функционал, основной сценарий (smoke)
     - Средний: основной функционал, стандартные сценарии
     - Низкий: второстепенный функционал, edge cases

4.2. Статус тест-кейса должен быть актуальным:
     - Готов: кейс прошёл ревью и готов к выполнению
     - Ревью: кейс на проверке
     - Черновик: кейс в разработке
     - Сломан: кейс неактуален или содержит ошибки

5. ПРАВИЛА РУССКОГО ЯЗЫКА
---------------------------
5.1. Текст должен быть написан грамотным русским языком.
5.2. Не допускаются орфографические ошибки.
5.3. Не допускаются пунктуационные ошибки.
5.4. Стиль изложения — официально-деловой, без разговорных выражений.
5.5. Используй повелительное наклонение для шагов: "Введите", "Нажмите", "Откройте"
     или инфинитив: "Ввести", "Нажать", "Открыть" (единообразно в рамках кейса).
5.6. Не используй жаргонизмы и сленг.
5.7. Названия полей, кнопок и элементов интерфейса заключай в кавычки или выделяй.
5.8. Избегай двусмысленности и неоднозначных формулировок.

6. ПОЛНОТА ПОКРЫТИЯ
--------------------
6.1. Тест-кейс должен проверять ОДИН конкретный сценарий.
     - Не объединяй несколько сценариев в один кейс.
     
6.2. Кейс должен быть воспроизводимым — любой тестировщик должен получить тот же результат.

6.3. Не должно быть шагов, зависящих от результата предыдущего шага (условных переходов).
     - Недопустимо: "Если появилось окно Х, то сделай Y, иначе Z"
